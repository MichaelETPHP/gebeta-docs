1. Project Overview

What is Bahirdar?

Bahirdar is a city-exclusive ride-hailing platform designed and built from the ground up for the roads, riders, and drivers of Bahir Dar, Ethiopia. Unlike global platforms that struggle with local road networks, payment infrastructure, and language barriers, Bahirdar is purpose-built for its city using Ethiopian mapping, local payment methods, and an interface tuned for the local context.

Platform Components

  • Rider Mobile App (React Native): passengers book and track rides in real time.
  • Driver Mobile App (React Native): drivers receive, navigate, and complete ride requests.
  • Node.js / Express Backend API: the central engine connecting all components.
  • React / Vite Admin Panel: the platform owner manages drivers, riders, fares, and analytics.

1.3 Business Model

Commission-Based Ride-Hailing

Bahirdar operates on a commission model. The current planning split is 15% retained by the platform and 85% kept by the driver. Pricing is calculated per trip using base fare plus distance rate plus time rate, all configurable from the Admin Panel.

Configurable Commission The 15% platform commission, 85% driver share, fare values, surge multipliers, and related payment numbers are changeable business settings. Treat them as current assumptions until finalized by the business team.
  • Platform commission: currently 15% of each completed fare.
  • Driver share: currently 85% of each completed fare.
  • Pricing: base fare + (km rate x distance) + (minute rate x duration).
  • Primary payment: cash, paid directly from rider to driver and logged in the app.
  • Roadmap payment: TeleBirr digital payments.
  • Surge pricing: configurable multiplier by zone and time, managed from the Admin Panel.

Technology Decision Rationale

OSRM vs Google Maps Directions API

The platform uses OSRM (Open Source Routing Machine) self-hosted on the VPS rather than a paid external routing API.

FactorDetail
CostOSRM is free with no per-request API billing or monthly caps.
LatencyOSRM on local VPS targets ~20-50ms compared with external API latency around ~150-300ms.
DataOSRM uses OpenStreetMap data with good Bahir Dar road coverage.
PrivacyRoute queries never leave the VPS, supporting full data sovereignty.
Offline resilienceOSRM keeps routing live even if internet connectivity is degraded.
LimitationNo real-time traffic; acceptable at Bahir Dar MVP scale.

Gebeta Maps vs Google Maps for Display

Gebeta Maps is an Ethiopian mapping company providing map tiles with accurate local road data, Amharic street names, and Ethiopian landmarks that global map providers often miss in secondary cities. This gives riders and drivers a familiar and accurate map experience.

Redis for Live Location

Driver GPS coordinates update every 3 seconds. Writing these directly to PostgreSQL would create unsustainable write load. Redis stores live locations as ephemeral key-value entries with a short TTL, while PostgreSQL receives periodic location flushes for historical records.

PostGIS for Nearest Driver Queries

PostGIS extends PostgreSQL with geospatial indexing. A GIST spatial index on driver location columns allows the matching engine to find the nearest available drivers within a target radius in under 50 milliseconds without an external geo-service.

3. Database Architecture

PostgreSQL and PostGIS Foundation

The platform uses PostgreSQL with the PostGIS extension, hosted on a self-hosted Supabase instance deployed via Coolify on a Hostinger VPS. The backend API connects through a connection pool, and PostGIS is enabled for all geospatial queries.

Core Table Structure

Users and Profiles

  • users: id, phone, name, email, role (rider/driver/admin), status (active/banned/pending), created_at.
  • driver_profiles: user_id FK, vehicle_type, plate_number, license_number, rating, total_trips, is_online, current_location (PostGIS POINT), documents_verified, verified_by_admin.
  • rider_profiles: user_id FK, default_payment_method, rating, total_rides, created_at.

Ride Flow Tables

  • ride_requests: id, rider_id, pickup_location (POINT), dropoff_location (POINT), status, estimated_fare, created_at.
  • rides: id, request_id, driver_id, rider_id, fare_amount, distance_km, duration_minutes, polyline, started_at, completed_at.
  • ride_status_logs: ride_id, status, actor_id, timestamp, with a full audit trail for every status change.

Payments

  • payments: id, ride_id, rider_id, driver_id, gross_amount, configurable platform_fee, configurable driver_payout, method (cash/telebirr), status, created_at.
  • driver_earnings: driver_id, period_type, period_start, total_rides, gross_earned, platform_deducted, net_earned.

Location and Routing

  • driver_locations: driver_id, location (POINT), heading, speed, updated_at, synced from Redis every 30 seconds for historical records.
  • zones: id, name, boundary (POLYGON), fare_multiplier, is_active, used for service areas and surge zones.
  • saved_places: user_id, label (Home/Work/Other), location (POINT), address_text, created_at.

Configuration and Admin

  • fare_config: vehicle_type, base_fare, per_km_rate, per_minute_rate, minimum_fare, currency, updated_at.
  • app_settings: key, value, updated_by, updated_at, used for platform-wide feature toggles.
  • notifications: id, user_id, type, title, body, is_read, created_at.
  • otp_records: phone, code (hashed), expires_at, used, stored in Redis rather than PostgreSQL.

Spatial Index Strategy

GIST indexes are placed on all PostGIS geometry columns for fast spatial lookups. The most critical index is on driver_locations.location, allowing the nearest-driver query to scan geometrically relevant rows rather than the entire table. At 200 online drivers, this query executes in under 5ms.

4. Sign-In Methods

How Riders and Drivers Log In

The Rider app offers three ways to sign in. The Driver app offers one. All three issue the exact same kind of session at the end — a JWT access token plus a refresh token — so nothing downstream in the app needs to know or care which method a person used.

Phone Number + OTP (Default)

  • App opens with a Bahirdar branded splash screen.
  • Rider or driver enters their phone number and receives a 6-digit OTP through Afro Message SMS.
  • OTP is checked against the code stored in Redis (5-minute expiry).
  • JWT access token and refresh token are issued on success.
  • New accounts finish a short profile setup (name, optional photo) before reaching the home screen.

Google Sign-In (Rider App)

One tap, no phone number needed. The app never gets to simply say "trust me, this is a Google account" — the token it hands the backend is independently checked against Google's own servers before anything is trusted.

  • Rider taps the Google button; the native Google account picker opens.
  • Google returns a signed ID token to the app.
  • The app sends that token to the backend, which re-verifies it directly with Google (never trusts the app's word for who signed in).
  • The backend looks the person up by google_id — a fixed ID from Google that never changes, unlike an email address.
  • If this Google account already has a Bahirdar account (matched by verified email), it's linked instead of creating a duplicate.
  • If it's a first-time sign-in with no match, a new rider account is created with no phone number attached.

Sign in with Apple (Rider App, iOS Only)

Works the same way as Google Sign-In — same verify-then-match pattern, keyed on apple_id instead of google_id.

  • Only shows on iOS — Apple Sign-In does not exist on Android, so the button hides itself there automatically.
  • Apple returns a signed identity token; the backend re-verifies it against Apple's own public keys before trusting it.
  • Matched by apple_id first, then by verified email if this is the account's first time linking.
Why This Exists Apple's App Store rule 4.8 requires that any app offering a third-party social login on iOS (Google, Facebook, etc.) must also offer Sign in with Apple. The Rider app already had Google Sign-In, so this was a requirement for App Store approval — not an optional extra.
Two Apple Quirks Handled Automatically Apple only shares the person's name once — on that Apple ID's very first authorization ever on this app. It is saved immediately, because it is never sent again on later logins. Apple can also give a private relay email (like abc123@privaterelay.appleid.com) instead of the real one — this is normal and is stored as the account's email as-is.

5. Rider App Workflow

Complete Passenger Experience

Once signed in (see Sign-In Methods above), the rider lands on the home screen with Gebeta Map centered on Bahir Dar and moves through the flow below.

Booking a Ride

  • Rider sees the city map with live GPS location.
  • Rider taps "Where to?" and opens destination search.
  • Rider types a destination name or taps the map to pin a dropoff point.
  • OSRM calculates road distance, duration, and route polyline.
  • Route is drawn from pickup to dropoff in blue.
  • Fare estimate appears using base fare, distance rate, and minute rate.
  • Rider reviews fare and taps "Request Ride".
  • A ride_request record is created with status pending and the matching engine activates immediately.

Waiting for Match

  • Rider sees animated search: "Looking for a nearby driver..."
  • Available driver dots are visible on the surrounding map.
  • Matching engine identifies and notifies the best available driver.
  • When the driver accepts, a driver profile card appears with name, photo, vehicle type, plate number, and rating.
  • Live ETA is calculated from OSRM for driver-to-pickup routing.
  • Driver location dot animates toward pickup in real time.
  • Push notification confirms: "Your driver is on the way".

Driver En Route to Pickup

  • Rider watches the driver move on the map in real time with 3-second updates.
  • ETA countdown updates as the driver approaches.
  • Rider can call the driver through in-app masked call.
  • Rider can cancel before driver arrival, subject to cancellation policy.
  • Driver taps "I Have Arrived" and the rider receives a push notification.

Active Trip

  • Driver taps "Start Trip", starting trip timer and fare meter.
  • Status updates to in_progress on both apps.
  • Rider sees live map, route, and current vehicle position.
  • Estimated arrival to destination updates during the ride.
  • SOS emergency button remains visible.

Trip Completion and Payment

  • Driver taps "End Trip" at destination.
  • Final fare is calculated from actual distance and duration.
  • Fare breakdown screen appears to the rider.
  • Cash payment: rider pays driver the displayed amount directly.
  • App records payment and ride status changes to completed.
  • Rider rates driver from 1-5 stars with optional text comment.
  • Trip is added to ride history.

Additional Rider Features

  • Ride History with route replay, fare details, and driver information.
  • Saved Places for Home, Work, and custom favorites with map pinning.

7. Ride Matching Engine

How Matching Works

The matching engine runs on the backend as soon as a ride_request record is created.

  • Rider submits ride request and backend receives pickup GPS coordinates.
  • Backend reads all online drivers from Redis with sub-10ms lookup.
  • PostGIS filters drivers within 5km of pickup.
  • Top 10 nearest drivers are returned and sorted by straight-line proximity.
  • OSRM calculates actual road distance from each driver to pickup for accuracy.
  • Drivers are scored by road distance (70%), rating (20%), and acceptance rate (10%).
  • Highest-scored driver receives ride request through Socket.io.
  • Driver has a 30-second response window.
  • On accept, the ride is assigned and all other candidates stand down.
  • On decline or timeout, the next driver in the ranked list receives the request.
  • If all candidates are exhausted, the rider is notified that no drivers are available nearby.
SELECT driver_id, ST_Distance(location, $pickup) AS dist
FROM driver_locations
WHERE is_available = true
ORDER BY dist ASC
LIMIT 10;

  • If a selected driver goes offline, the next candidate receives the request immediately.
  • If the rider cancels before acceptance, all pending notifications are cancelled from the queue.
  • If no drivers are within 5km, radius expands to 10km and rider is notified of longer wait.
  • If a driver has a trip just completing, they are excluded from matching until trip status closes.
8. Fare & Commission Calculation

Fare Formula

The final fare is calculated at trip completion using actual measured trip data rather than only the pre-trip estimate.

Final Fare = Base Fare + (Distance km x Per-km Rate) + (Duration min x Per-minute Rate)
Final Fare = max(calculated, Minimum Fare)
If Surge Active: Final Fare = Final Fare x Surge Multiplier

10. Real-Time Architecture

Socket.io Event Flows

Driver Location Streaming

  • Driver emits driver:location_update every 3 seconds with lat, lng, heading, and speed.
  • Backend receives the event and writes to Redis key driver:{id}:location with 10-second TTL.
  • If driver has an active ride, backend broadcasts rider:driver_location to rider socket room.
  • Redis flushes to PostgreSQL driver_locations table every 30 seconds for historical records.

Ride Request Dispatch

  • Backend emits driver:ride_request to the selected driver with full request payload.
  • Driver emits driver:accept_ride or driver:decline_ride.
  • On accept, backend emits rider:driver_assigned with driver profile and ETA.

Trip Status Events

  • driver:arrived is relayed to rider through rider:driver_arrived push and socket.
  • driver:trip_started updates the database and emits rider:trip_started.
  • driver:trip_ended calculates fare and emits rider:trip_ended with fare breakdown.

Redis Architecture

Redis serves three distinct roles: live location storage, Socket.io adapter support for broadcasting across backend instances, and rate limiting for OTP and API abuse prevention.

Development SSH Tunnels

During local development, two SSH tunnels connect to VPS-hosted services before the dev server starts.

ssh -L 6379:localhost:6379 user@vps_ip   # Redis tunnel
ssh -L 5000:localhost:5000 user@vps_ip   # OSRM tunnel

Both tunnels must be active before running the backend development server.

12. SMS & Push Notifications

Messaging Infrastructure

SMS Provider - Afro Message

Afro Message (afromessage.com) is the SMS API used for OTP delivery and every other outgoing SMS on the platform. It routes through Ethiopian carriers such as Ethio Telecom and Safaricom Ethiopia for reliable local delivery, which is preferred over global providers with unreliable routes into Ethiopia.

  • OTP length: 4 digits (e.g. 1234) — generated with a cryptographically secure random number, not a simple counter.
  • OTP expiry: 10 minutes. Stored in the PostgreSQL otp_codes table (not Redis — Redis on this platform is reserved for driver location/matching, never for OTPs).
  • Resend cooldown: 60 seconds minimum gap between two OTP sends to the same number, on top of the 3-per-10-minute limit below.
  • Rate limit: 3 OTP sends per 10-minute window per phone number, to prevent abuse.
  • Delivery target: under 10 seconds to Ethiopian numbers.

How Sending Actually Works

The backend calls Afro Message's REST API directly with the API key, a sender name the recipient sees (currently "BAHIRDAR"), the destination number, and the message text. Afro Message replies with a success/failure acknowledgement and a message ID used for tracking. No SDK is involved — it's a plain authenticated HTTP call.

Every Message Type Sent, Not Just OTP

The same SMS system also sends 8 other message types, all through one shared delivery + logging path:

  • OTP — phone login/registration codes.
  • Trip receipt — sent to the rider when a trip completes (pickup, dropoff, total fare).
  • Trip assignment — used by the call-center booking flow, with the assigned driver's car and ETA.
  • Driver approval / Driver suspension — account status changes made from the Admin Panel.
  • Driver registration reminder — nudges a driver who started but didn't finish signup.
  • Rider suspension / Rider welcome back — same idea, rider side.
  • Custom admin — a free-text message an admin can send to any one phone number.

Every Attempt Is Logged, Not Just Successes

Every SMS attempt — sent, failed, or skipped (because Afro Message isn't configured) — is recorded in the platform_sms_logs table. This is what powers the "SMS History" list on a rider or driver's detail page in the Admin Panel, so support staff can see exactly what was sent to a given phone number and whether it actually went through.

Dev/Local Fallback — No API Key Needed to Test

When AFROMESSAGE_API_KEY is left blank (the default for local development), no real SMS is sent. Instead, the OTP is printed straight to the server console, and the fixed code 1234 is always accepted as a universal dev bypass, on any phone number. Every skipped-because-unconfigured attempt is still logged the same as a real one, so the Admin Panel's SMS History looks the same in dev and production.

Push Notifications — Two Paths, Not Just FCM

Push notifications actually run through two different systems, chosen by how time-critical the alert is, and they work on both Android and iOS for both apps, not Android-only.

  • Firebase Cloud Messaging (FCM) — a queued batch sender, used for most notifications (trip completed, driver approved/rejected, account status changes, admin broadcasts). These go through a background worker job, not sent instantly one-by-one.
  • Expo Push Notifications — a separate, direct (non-queued) path used only where a delay is unacceptable: a new trip offer reaching a driver whose app is backgrounded or closed, and an incoming in-app voice call ringing on a backgrounded/closed app. Both skip the FCM queue entirely and go straight out for speed.

Rider Notifications

  • Driver arrived at pickup.
  • Trip started.
  • Trip completed with fare summary.
  • Ride cancelled by driver or system.

Driver Notifications

  • New ride request, also delivered via Socket.io for speed.
  • Rider cancelled before pickup.
  • Account approved by admin.
  • Account rejected by admin with reason included.

Admin Broadcast

The owner can send custom push notifications to all riders, all drivers, or specific users from the Admin Panel.

Admin Live Alerts — New Trip Requests

The Admin Panel shows a live alert card the moment any rider requests a trip, with no page refresh needed.

  • Every admin browser tab joins a shared Socket.io admin room automatically on login, based on the account's role in the JWT.
  • When a trip is created, the backend broadcasts admin:trip:requested to that room with the rider's name, phone, avatar, pickup, dropoff, and estimated fare.
  • The card appears in the corner with a ring sound, the rider's photo and phone number, and an expandable details toggle for pickup/dropoff.
  • It stays on screen for 2 minutes and repeats the ring every 15 seconds so a new request is never missed in a busy dashboard.
  • "View Trip" deep-links straight into that trip's detail panel on the Trips page — not just the general trip list.

In-App Voice Calling

Riders and drivers can call each other from inside the app during an active trip, without exposing either person's real phone number. Admins can also call a rider from the Trip Details page in the Admin Panel — on any trip, including completed ones — which is the fallback for riders who signed up with Google or Apple and have no phone number on record at all.

  • Built on WebRTC (audio-only) with call setup relayed through Socket.io, not a phone carrier.
  • Signaling messages route through each person's private user:{id} socket room, so a call still connects correctly even if one side briefly reconnects mid-trip.
  • A 45-second watchdog ends the call attempt automatically if the other side never answers.
  • Real native call UI on both platforms — CallKit on iOS, ConnectionService on Android — so an incoming in-app call rings and can be answered like a normal phone call, including from the lock screen.
  • Rider ↔ driver calling is only offered while a trip is active. Admin → rider support calling is the one exception and works on any trip status.

STUN and TURN, in Plain Terms

Two things have to happen for an in-app call to actually carry sound: the two devices need to find each other on the internet, and then audio needs an actual path to travel between them. STUN and TURN are two different tools for that second part.

TermWhat It Actually DoesWhen It's Used
STUNHelps each device discover its own real public address on the internet, so the two devices can try to connect to each other directly — audio flows phone-to-phone (or phone-to-browser), never touching our own servers.Works most of the time. This is the only thing set up on this platform today.
TURNA relay server both sides send audio to when a direct connection isn't possible (common on strict office Wi-Fi, or when a phone's mobile-data network blocks direct connections). Audio now flows through this server instead of directly.Not set up yet on this platform — this is the current gap. Its absence is the most likely reason a call can get stuck on "Connecting" for some device/network combinations.
Why This Matters Right Now Admin calling adds a new combination that didn't exist before: a browser (Admin Panel) on one network calling a phone on mobile data on a completely different network. That specific combination is exactly the case STUN alone struggles with. A working TURN server is the real fix, not a code change.

13.1 Manual Play Store Submit

Play Store Manual Build & Submit (EAS Quota Fallback)

Both BahirdarDriver and BahirdarRide normally ship to the Play Store through EAS Build's free-tier cloud queue, which auto-submits on completion. That free tier has a monthly build quota. Once it runs out mid-month, this manual fallback builds the signed Android App Bundle locally with Gradle, then hands it to eas-cli for the actual Play Store upload. The two apps share the exact same process — only the project folder and keystore details differ.

15. Known Issues & Fixes

Real Bugs Found and Fixed

A running log of real production bugs found during development, why they happened, and how they were fixed — kept here so the same mistake is never re-debugged twice.

Trip Lifecycle

SymptomRoot CauseFix
Driver accepts a trip after the rider was already told "no drivers found"The rider was notified before the trip's status was updated in the database — a driver could accept in that gap.Status is now written to the database first, then the rider is notified — closing the race window.
Trip offer push notifications silently never arrived to driversThe push-token lookup query sorted by a database column (updated_at) that doesn't exist on that table.Query fixed to sort by the real column, last_used_at.
Driver swipes "Complete Trip" and sees "Trip not found" — but the trip is actually completedA slow network response (or a duplicate tap) sent a second completion request after the first one had already succeeded. The second request correctly found nothing left "in progress" and returned a scary-looking error, even though nothing was wrong.Completing a trip is now idempotent — a repeat request for an already-completed trip returns the same success result instead of an error. Applied to all three trip-progress steps (arrived, started, completed).
Every driver trip-rejection crashed at the database layerThe code tried to save the value 'rejected' into a column that only allows 'declined'.Response and status values are now mapped correctly before saving.
Driver cancelling a trip never notified the rider in real timeThe socket event name used to notify the rider (TRIP_CANCELLED) was referenced in code but never actually defined anywhere — it was silently sending to nothing.The missing event constant was added, matching the name the rider app already listens for.

Admin token refresh (POST /admin/refresh) was guaranteed to crashThe route pointed at a function that was never written.The missing function was added, matching the same pattern already used for rider and driver token refresh.
