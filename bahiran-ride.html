1. Project Overview

What is Bahirdar?

Bahirdar is a city-exclusive ride-hailing platform designed and built from the ground up for the roads, riders, and drivers of Bahir Dar, Ethiopia. Unlike global platforms that struggle with local road networks, payment infrastructure, and language barriers, Bahirdar is purpose-built for its city using Ethiopian mapping, local payment methods, and an interface tuned for the local context.

Platform Components

  • Rider Mobile App (React Native): passengers book and track rides in real time.
  • Driver Mobile App (React Native): drivers receive, navigate, and complete ride requests.
  • Node.js / Express Backend API: the central engine connecting all components.
  • React / Vite Admin Panel: the platform owner manages drivers, riders, fares, and analytics.

1.3 Business Model

Commission-Based Ride-Hailing

Bahirdar operates on a commission model. The current planning split is 15% retained by the platform and 85% kept by the driver. Pricing is calculated per trip using base fare plus distance rate plus time rate, all configurable from the Admin Panel.

Configurable Commission The 15% platform commission, 85% driver share, fare values, surge multipliers, and related payment numbers are changeable business settings. Treat them as current assumptions until finalized by the business team.
  • Platform commission: currently 15% of each completed fare.
  • Driver share: currently 85% of each completed fare.
  • Pricing: base fare + (km rate x distance) + (minute rate x duration).
  • Primary payment: cash, paid directly from rider to driver and logged in the app.
  • Roadmap payment: TeleBirr digital payments.
  • Surge pricing: configurable multiplier by zone and time, managed from the Admin Panel.

Technology Decision Rationale

OSRM vs Google Maps Directions API

The platform uses OSRM (Open Source Routing Machine) self-hosted on the VPS rather than a paid external routing API.

FactorDetail
CostOSRM is free with no per-request API billing or monthly caps.
LatencyOSRM on local VPS targets ~20-50ms compared with external API latency around ~150-300ms.
DataOSRM uses OpenStreetMap data with good Bahir Dar road coverage.
PrivacyRoute queries never leave the VPS, supporting full data sovereignty.
Offline resilienceOSRM keeps routing live even if internet connectivity is degraded.
LimitationNo real-time traffic; acceptable at Bahir Dar MVP scale.

Gebeta Maps vs Google Maps for Display

Gebeta Maps is an Ethiopian mapping company providing map tiles with accurate local road data, Amharic street names, and Ethiopian landmarks that global map providers often miss in secondary cities. This gives riders and drivers a familiar and accurate map experience.

Redis for Live Location

Driver GPS coordinates update every 3 seconds. Writing these directly to PostgreSQL would create unsustainable write load. Redis stores live locations as ephemeral key-value entries with a short TTL, while PostgreSQL receives periodic location flushes for historical records.

PostGIS for Nearest Driver Queries

PostGIS extends PostgreSQL with geospatial indexing. A GIST spatial index on driver location columns allows the matching engine to find the nearest available drivers within a target radius in under 50 milliseconds without an external geo-service.

3. Database Architecture

PostgreSQL and PostGIS Foundation

The platform uses PostgreSQL with the PostGIS extension, hosted on a self-hosted Supabase instance deployed via Coolify on a Hostinger VPS. The backend API connects through a connection pool, and PostGIS is enabled for all geospatial queries.

Core Table Structure

Users and Profiles

  • users: id, phone, name, email, role (rider/driver/admin), status (active/banned/pending), created_at.
  • driver_profiles: user_id FK, vehicle_type, plate_number, license_number, rating, total_trips, is_online, current_location (PostGIS POINT), documents_verified, verified_by_admin.
  • rider_profiles: user_id FK, default_payment_method, rating, total_rides, created_at.

Ride Flow Tables

  • ride_requests: id, rider_id, pickup_location (POINT), dropoff_location (POINT), status, estimated_fare, created_at.
  • rides: id, request_id, driver_id, rider_id, fare_amount, distance_km, duration_minutes, polyline, started_at, completed_at.
  • ride_status_logs: ride_id, status, actor_id, timestamp, with a full audit trail for every status change.

Payments

  • payments: id, ride_id, rider_id, driver_id, gross_amount, configurable platform_fee, configurable driver_payout, method (cash/telebirr), status, created_at.
  • driver_earnings: driver_id, period_type, period_start, total_rides, gross_earned, platform_deducted, net_earned.

Location and Routing

  • driver_locations: driver_id, location (POINT), heading, speed, updated_at, synced from Redis every 30 seconds for historical records.
  • zones: id, name, boundary (POLYGON), fare_multiplier, is_active, used for service areas and surge zones.
  • saved_places: user_id, label (Home/Work/Other), location (POINT), address_text, created_at.

Configuration and Admin

  • fare_config: vehicle_type, base_fare, per_km_rate, per_minute_rate, minimum_fare, currency, updated_at.
  • app_settings: key, value, updated_by, updated_at, used for platform-wide feature toggles.
  • notifications: id, user_id, type, title, body, is_read, created_at.
  • otp_records: phone, code (hashed), expires_at, used, stored in Redis rather than PostgreSQL.

Spatial Index Strategy

GIST indexes are placed on all PostGIS geometry columns for fast spatial lookups. The most critical index is on driver_locations.location, allowing the nearest-driver query to scan geometrically relevant rows rather than the entire table. At 200 online drivers, this query executes in under 5ms.

4. Rider App Workflow

Complete Passenger Experience

Onboarding

  • App opens with a Bahirdar branded splash screen.
  • Rider enters phone number and receives OTP through Afro Message SMS.
  • Rider enters 6-digit OTP, verified against Redis-stored OTP.
  • JWT access token and refresh token are issued on success.
  • Rider completes profile setup with name and optional profile photo.
  • Home screen loads with Gebeta Map centered on Bahir Dar.

Booking a Ride

  • Rider sees the city map with live GPS location.
  • Rider taps "Where to?" and opens destination search.
  • Rider types a destination name or taps the map to pin a dropoff point.
  • OSRM calculates road distance, duration, and route polyline.
  • Route is drawn from pickup to dropoff in blue.
  • Fare estimate appears using base fare, distance rate, and minute rate.
  • Rider reviews fare and taps "Request Ride".
  • A ride_request record is created with status pending and the matching engine activates immediately.

Waiting for Match

  • Rider sees animated search: "Looking for a nearby driver..."
  • Available driver dots are visible on the surrounding map.
  • Matching engine identifies and notifies the best available driver.
  • When the driver accepts, a driver profile card appears with name, photo, vehicle type, plate number, and rating.
  • Live ETA is calculated from OSRM for driver-to-pickup routing.
  • Driver location dot animates toward pickup in real time.
  • Push notification confirms: "Your driver is on the way".

Driver En Route to Pickup

  • Rider watches the driver move on the map in real time with 3-second updates.
  • ETA countdown updates as the driver approaches.
  • Rider can call the driver through in-app masked call.
  • Rider can cancel before driver arrival, subject to cancellation policy.
  • Driver taps "I Have Arrived" and the rider receives a push notification.

Active Trip

  • Driver taps "Start Trip", starting trip timer and fare meter.
  • Status updates to in_progress on both apps.
  • Rider sees live map, route, and current vehicle position.
  • Estimated arrival to destination updates during the ride.
  • SOS emergency button remains visible.

Trip Completion and Payment

  • Driver taps "End Trip" at destination.
  • Final fare is calculated from actual distance and duration.
  • Fare breakdown screen appears to the rider.
  • Cash payment: rider pays driver the displayed amount directly.
  • App records payment and ride status changes to completed.
  • Rider rates driver from 1-5 stars with optional text comment.
  • Trip is added to ride history.

Additional Rider Features

  • Ride History with route replay, fare details, and driver information.
  • Saved Places for Home, Work, and custom favorites with map pinning.
  • Profile Settings for name, photo, and phone number.
  • Notifications Inbox for ride updates and platform announcements.
  • In-App Support for contacting support directly from the app.
5. Driver App Workflow

Driver Operations Lifecycle

Driver Registration and Verification

  • Driver downloads the app and registers by phone number with OTP verification.
  • Driver submits full name, photo, and national ID upload.
  • Vehicle registration includes type (bajaj/taxi/car), plate number, and vehicle photo.
  • Driver uploads license photo and submits documents for Admin Panel review.
  • Admin approves or rejects documents with a written reason.
  • Driver receives push notification of approval or rejection.
  • Approved drivers are activated and can go online.

Going Online

  • Driver opens app with Offline status by default.
  • Driver toggles "Go Online".
  • App streams GPS coordinates every 3 seconds through Socket.io.
  • Backend writes location to Redis as driver:{id}:location with 10-second TTL.
  • Driver is marked available in the matching pool and appears on nearby rider maps.

Receiving a Ride Request

  • Matching engine identifies the driver as the best candidate.
  • Ride request popup shows rider pickup point on mini-map, estimated distance to rider, destination area, and estimated fare.
  • Driver has a 30-second countdown to accept or decline.
  • Accept assigns the ride and launches in-app navigation to pickup.
  • Decline or timeout sends the request to the next driver in the match queue.

Pickup and Active Trip Navigation

  • Gebeta Maps navigation launches automatically with route to pickup.
  • Driver live location streams to rider app every 3 seconds.
  • Driver arrives and taps "I Have Arrived".
  • Driver can call rider through in-app masked call.
  • Driver taps "Start Trip", triggering fare meter and timer.
  • Gebeta Maps shows the route to destination while GPS continues streaming to the rider.
  • Driver arrives at destination and taps "End Trip".

Trip Completion and Dashboard

  • Final fare is displayed to the driver.
  • Driver shows fare to rider and collects cash.
  • Driver rates rider from 1-5 stars.
  • Trip is logged to history and earnings update in the dashboard.
  • Driver automatically returns to Online status for the next ride.
  • Dashboard shows today's trips, gross earned, platform fee, net earned, weekly/monthly history, ratings, vehicle documents, and payout history roadmap.
6. Ride Matching Engine

How Matching Works

The matching engine runs on the backend as soon as a ride_request record is created.

  • Rider submits ride request and backend receives pickup GPS coordinates.
  • Backend reads all online drivers from Redis with sub-10ms lookup.
  • PostGIS filters drivers within 5km of pickup.
  • Top 10 nearest drivers are returned and sorted by straight-line proximity.
  • OSRM calculates actual road distance from each driver to pickup for accuracy.
  • Drivers are scored by road distance (70%), rating (20%), and acceptance rate (10%).
  • Highest-scored driver receives ride request through Socket.io.
  • Driver has a 30-second response window.
  • On accept, the ride is assigned and all other candidates stand down.
  • On decline or timeout, the next driver in the ranked list receives the request.
  • If all candidates are exhausted, the rider is notified that no drivers are available nearby.
SELECT driver_id, ST_Distance(location, $pickup) AS dist
FROM driver_locations
WHERE is_available = true
ORDER BY dist ASC
LIMIT 10;

Edge Cases

  • If a selected driver goes offline, the next candidate receives the request immediately.
  • If the rider cancels before acceptance, all pending notifications are cancelled from the queue.
  • If no drivers are within 5km, radius expands to 10km and rider is notified of longer wait.
  • If a driver has a trip just completing, they are excluded from matching until trip status closes.
7. Fare & Commission Calculation

Fare Formula

The final fare is calculated at trip completion using actual measured trip data rather than only the pre-trip estimate.

Final Fare = Base Fare + (Distance km x Per-km Rate) + (Duration min x Per-minute Rate)
Final Fare = max(calculated, Minimum Fare)
If Surge Active: Final Fare = Final Fare x Surge Multiplier

9. Real-Time Architecture

Socket.io Event Flows

Driver Location Streaming

  • Driver emits driver:location_update every 3 seconds with lat, lng, heading, and speed.
  • Backend receives the event and writes to Redis key driver:{id}:location with 10-second TTL.
  • If driver has an active ride, backend broadcasts rider:driver_location to rider socket room.
  • Redis flushes to PostgreSQL driver_locations table every 30 seconds for historical records.

Ride Request Dispatch

  • Backend emits driver:ride_request to the selected driver with full request payload.
  • Driver emits driver:accept_ride or driver:decline_ride.
  • On accept, backend emits rider:driver_assigned with driver profile and ETA.

Trip Status Events

  • driver:arrived is relayed to rider through rider:driver_arrived push and socket.
  • driver:trip_started updates the database and emits rider:trip_started.
  • driver:trip_ended calculates fare and emits rider:trip_ended with fare breakdown.

Redis Architecture

Redis serves three distinct roles: live location storage, Socket.io adapter support for broadcasting across backend instances, and rate limiting for OTP and API abuse prevention.

Development SSH Tunnels

During local development, two SSH tunnels connect to VPS-hosted services before the dev server starts.

ssh -L 6379:localhost:6379 user@vps_ip   # Redis tunnel
ssh -L 5000:localhost:5000 user@vps_ip   # OSRM tunnel

Both tunnels must be active before running the backend development server.

Scalability Design

The current infrastructure targets up to 500 concurrent riders and 200 online drivers, sufficient for Bahir Dar MVP scale on the Hostinger VPS.

  • Redis clustering handles increased socket adapter load as connections grow.
  • PostgreSQL read replicas are added when reporting queries impact write performance.
  • OSRM horizontal scaling adds a second routing instance behind a load balancer for routing surge.
  • Backend horizontal scaling uses Redis Pub/Sub adapter so multiple backend pods can share socket events.
11. SMS & Push Notifications

Messaging Infrastructure

SMS Provider - Afro Message

Afro Message (afromessage.com) is the SMS API used for OTP delivery. It routes through Ethiopian carriers such as Ethio Telecom and Safaricom Ethiopia for reliable local delivery, which is preferred over global providers with unreliable routes into Ethiopia.

  • OTP length: 6 digits.
  • OTP expiry: 5 minutes, stored as TTL in Redis rather than PostgreSQL.
  • Max resend attempts: 3 per 10-minute window, rate limited to prevent abuse.
  • Delivery target: under 10 seconds to Ethiopian numbers.

Firebase Cloud Messaging

FCM handles all push notifications for both Android apps.

Rider Notifications

  • Driver assigned and on the way.
  • Driver arrived at pickup.
  • Trip started.
  • Trip completed with fare summary.
  • Ride cancelled by driver or system.

Driver Notifications

  • New ride request, also delivered via Socket.io for speed.
  • Rider cancelled before pickup.
  • Account approved by admin.
  • Account rejected by admin with reason included.

Admin Broadcast

The owner can send custom push notifications to all riders, all drivers, or specific users from the Admin Panel.
