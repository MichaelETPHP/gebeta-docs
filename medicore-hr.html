1. Project Overview

What is MediCore HR?

A full-stack HR onboarding platform for hospital staff: officer login → side-menu dashboard → officer-scoped employee register → onboarding wizard in a modal → per-document verification that drives each employee's onboarding status.

  • Roles: hr_officer (only sees employees they registered), admin (sees everyone, can reassign ownership), viewer (read-only, no PII reveal/export).
  • Security: AES-256-GCM field-level encryption for national ID / bank account / pension / TIN, argon2id password hashing, revocable server-side sessions, full audit log.
  • Localization: English/Amharic UI, Ethiopian-calendar date picker for onboarding dates.

3. Local Setup

Getting the App Running

  1. 1Install Bun and Git for Windows.
  2. 2Clone the repo (see Cloning & Login below).
  3. 3Run bun install from the repo root.
  4. 4Get apps/api/.env from the team lead through a secure channel (see Sharing Secrets Safely) and place it at apps/api/.env.
  5. 5Run start-medicore.bat (Windows) — opens the API and web app in separate windows.
cmd# or run each manually, from the repo root:
bun run dev:api    # Hono API  -> http://localhost:3000
bun run dev:web    # SvelteKit -> http://localhost:5173
3.1 Environment Variables

apps/api/.env

Never committed — gitignored on purpose. apps/api/.env.example in the repo documents every key with no real values; get the real file from the team lead (see Sharing Secrets Safely).

  • DATABASE_URL — shared dev Postgres connection string.
  • JWT_SECRET, JWT_ACCESS_EXPIRES_IN, JWT_REFRESH_EXPIRES_IN — auth token signing/lifetimes.
  • ENCRYPTION_KEY — AES-256-GCM key for PII fields at rest. Must match whatever key already encrypted data in the shared DB — never rotate casually.
  • CORS_ORIGIN, PORT, FILE_BUCKET_DIR, AUTO_MIGRATE — server/runtime config.
Must Match Across the Team Since everyone points at the same shared dev database, JWT_SECRET and ENCRYPTION_KEY must be identical in everyone's .env, or tokens/decryption break across machines.

4.1 Cloning & Login

First-Time Setup Per Machine

All three developers push through one shared GitHub account (deliverygebeta-oss) rather than individual accounts. Authentication uses a Personal Access Token (PAT), not the account's real password.

Step 1 — Clone

cmdgit clone https://github.com/deliverygebeta-oss/gebeta-medi-core-hr-project.git
cd gebeta-medi-core-hr-project

Step 2 — Force token-based login (skip the browser OAuth popup)

By default, Git Credential Manager tries to open a browser and log in interactively — that needs the real account password, which nobody but the team lead should need. This forces a plain username/token prompt instead:

cmdgit config credential.https://github.com.provider generic

Step 3 — Trigger the credential prompt

cmdgit fetch

When prompted:

  • Username: deliverygebeta-oss
  • Password: the current shared token (ask the team lead — see Sharing Secrets Safely)

Git Credential Manager caches this afterward, so it's a one-time step per machine.

4.2 Daily Workflow

Pushing & Pulling Changes

  1. 1Always git pull origin dev before starting work, to avoid conflicts with a teammate's changes.
  2. 2Make your changes, then stage and commit normally.
  3. 3Push straight to dev — that's the working branch for all day-to-day changes.
  4. 4Once a set of changes has been tested and is ready to go live, fast-forward prod to match dev.
cmdgit pull origin dev
# ...make changes...
git add .
git commit -m "describe the change"
git push origin dev
Since everyone pushes through the same account, there's no GitHub-side record of which developer made a given push. If that matters for a specific change, mention your name in the commit message body.
4.3 Commit Identity

Keep Commits Looking Uniform

Right after cloning, set the local (repo-only) git identity so commits show as the team, not your personal name — this does not touch your global git config used by other projects:

cmdgit config user.name "MediCore Team"
git config user.email "team@medicore.local"
Required, Not Optional Skipping this step means your commits will show your personal GitHub-linked name/email on a shared team repo. Run it once per machine, right after cloning.
4.4 Sharing Secrets Safely

The Shared Token and .env File

Two things get shared outside of git: the GitHub access token, and apps/api/.env. Both contain real secrets.

  • Use a password manager's shared vault (1Password, Bitwarden), or an encrypted transfer — never Slack, email, or any chat, including AI assistants.
  • If a token or key is ever pasted into plaintext chat, treat it as compromised: revoke and regenerate it immediately rather than continuing to use it.
  • If someone leaves the team, rotate the shared token — there's no way to revoke access for just one person under a shared-account model.
5. Team & Access Model

Why a Shared Account?

This repo uses one shared GitHub login for all 3 developers instead of individual collaborator accounts. That's a deliberate tradeoff:

GainedGiven up
Simple setup — one token, no per-person invitesNo per-developer audit trail on GitHub (pushes all show as the shared account)
No org-seat management overheadOne leaked token affects everyone; no selective revocation for a single person
6. Troubleshooting

Common Issues

Push rejected with a 403 / "Permission denied"

The cached credential on your machine doesn't have access, or the shared token was rotated. Re-run git config credential.https://github.com.provider generic and re-trigger the prompt with the current token.

Cannot find module '.../vite/bin/vite.js'

Dependencies are missing or the install is corrupted. From the repo root: delete node_modules in the root, apps/web, and apps/api, then run bun install again.

My commits show my personal name, not "MediCore Team"

The repo-local git identity wasn't set on this machine (or was reset by another tool). Re-run the two git config commands in Commit Identity above.
