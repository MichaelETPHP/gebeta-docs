Taxi App Play Store Auto-Submit

Manual build-and-submit path for pushing BahirdarDriver and BahirdarRide Android app updates to the Google Play Store when the EAS free-tier cloud build quota is used up. Proven working for both apps on Windows.

Shell Requirement Every command on this page must run in Command Prompt (cmd.exe), not PowerShell. eas build --local does not work on Windows for Android, which is why this manual local-build path exists.

1. Introduction

Why This Path Exists

Both BahirdarDriver and BahirdarRide normally ship to the Play Store through EAS Build's free-tier cloud queue, which auto-submits on completion. That free tier has a monthly build quota. Once it runs out mid-month, cloud builds stop working until the quota resets — but a release doesn't have to wait. This page documents the manual fallback: build the signed Android App Bundle locally with Gradle, then hand it to eas-cli submit for the actual Play Store upload.

The two apps share the exact same process. Only the project folder and the release keystore details differ between them — every step below calls this out explicitly.

What This Covers

  • Regenerating the native Android project with Expo prebuild.
  • Wiring real release signing into build.gradle so the build isn't signed with the debug key.
  • Bumping versionCode so Play Console accepts the new build.
  • Producing a signed .aab with a local Gradle build.
  • Auto-submitting that .aab to the Play Store with eas-cli.
  • Verifying the upload landed and is in review.

Check Quota Before Starting

Confirm the EAS free-tier quota is actually the blocker before doing a manual build — it resets monthly.

Check remaining quota at expo.dev/accounts/zmichaeleth/settings/billing. If quota has already reset, skip this entire manual path and use the one-line cloud auto-submit command in When Cloud Quota Resets instead.
1.1 Prerequisites

Before You Start

  • Windows machine with Command Prompt (cmd.exe) — not PowerShell, not Git Bash, for every command on this page.
  • Node.js, npm, and a working Android SDK / Gradle toolchain already set up for local Expo builds.
  • npx eas-cli available in the project (no global install required — npx resolves it per project).
  • Access to the project root for whichever app you're building: BahirdarDriver or BahirdarRide, inside C:\SVELT_APP\CityBird-Bahirdar\.
  • The release keystore for that app, either in credentials\ in the project root or already documented below.
  • Play Console access to the corresponding app, to read the current highest versionCode from App bundle explorer.
  • Logged in to eas-cli with an account that has submit permission on the target app.
2. Step 1

Regenerate the Native Project

Start from the app's project root and regenerate the native Android project with Expo prebuild.

cmdcd C:\SVELT_APP\CityBird-Bahirdar\BahirdarDriver
:: or: cd C:\SVELT_APP\CityBird-Bahirdar\BahirdarRide

npx expo prebuild --platform android --clean
--clean Wipes Signing --clean wipes and regenerates the entire android\ folder every time, which resets versionCode back to 1 and resets release signing back to the debug key. Step 2 and Step 3 below must be redone every time you run this with --clean.

Shortcut: Skip --clean

If nothing native changed since your last build — no new native module, no app.json / app.config change — drop --clean:

cmdnpx expo prebuild --platform android

This does not wipe android\, so the signing config from last time is still there. Skip straight to Step 3.

3. Step 2

Wire Up Real Release Signing

Open android\app\build.gradle. In signingConfigs, add a release block next to debug. The keystore file, alias, and passwords differ between the two apps.

DDriver App

gradlerelease {
    storeFile file('bahirdar-driver-upload.jks')
    storePassword 'BahirdarDriver@2026'
    keyAlias 'upload'
    keyPassword 'BahirdarDriver@2026'
}

Copy the keystore into place:

cmdcopy credentials\bahirdar-driver-upload.jks android\app\bahirdar-driver-upload.jks

RRider App

The keystore and passwords are already saved in credentials.json at the project root — no need to re-download via eas-cli credentials.

gradlerelease {
    storeFile file('keystore.jks')
    storePassword '01259492296f768e8cdac8876a9e4540'
    keyAlias '9b2a40fd7f27272b4c43a6f83c9a9805'
    keyPassword 'd8ee7d3b7ac130c245990e5a842a3c59'
}

Copy the keystore into place:

cmdcopy credentials\android\keystore.jks android\app\keystore.jks

Point the Release Build at the New Config

For either app, in buildTypes { release { ... } } change:

gradlesigningConfig signingConfigs.debug   →   signingConfig signingConfigs.release
4. Step 3

Bump the Version Code

In Play Console, go to [App] → App bundle explorer and find the current highest versionCode across all tracks. In android\app\build.gradle, set versionCode to one higher than that number.

Check all tracks (Internal, Closed, Open, Production) — the highest versionCode across any of them is the one that matters, not just Production.
5. Step 4

Build the Signed .aab

cmdcd android
set NODE_ENV=production
gradlew.bat bundleRelease

Wait for BUILD SUCCESSFUL — typically 5–20 minutes on a cold run. Output lands at:

pathandroid\app\build\outputs\bundle\release\app-release.aab
6. Step 5

Auto-Submit

Run this from the app root, not from inside android\:

cmdcd C:\SVELT_APP\CityBird-Bahirdar\BahirdarDriver
npx eas-cli submit -p android --path android\app\build\outputs\bundle\release\app-release.aab

Expect:

output✓ Submitted your app to Google Play Store!
7. Step 6

Verify

  • Play Console → App bundle explorer — the new version code appears within minutes.
  • Play Console → Releases overview — the new release shows status "In review."

9. Reference

When Cloud Quota Resets

Once the EAS free-tier quota resets for the month, skip the entire manual build path above. Run this per app instead, from the app root:

cmdnpx eas-cli build -p android --profile production --non-interactive --no-wait --auto-submit

This queues a cloud build and auto-submits to the Play Store on completion — no local signing, no Gradle, no version-code bookkeeping by hand.

10. Reference

Troubleshooting

SymptomMost Likely Cause & Fix
Build is signed with the debug key--clean was run since the last release build, which resets signingConfig back to debug. Redo Step 2 before rebuilding.
versionCode already used--clean reset versionCode to 1, or the App bundle explorer number wasn't re-checked. Redo Step 3 against the current highest across all tracks.
Commands fail or behave unexpectedlyRunning in PowerShell or Git Bash instead of Command Prompt. Reopen a plain cmd.exe window and retry.
eas-cli submit can't find the .aab or fails immediatelySubmit was run from inside android\. It must run from the app root, as shown in Step 5.
Gradle build fails signing the release variantWrong keystore file copied into android\app\, or a driver/rider keystore value pasted into the wrong app's build.gradle. Recheck against Driver vs Rider Reference.
eas build --local fails on AndroidExpected — this does not work on Windows for Android. Use the manual Gradle path on this page instead.
Full Background For deeper troubleshooting and the reasoning behind this fallback path, see DEPLOYMENT_WITHOUT_EAS_PAID.md in the project root.
